# 调度器模块设计文档

## 任务与任务树概念

### 任务

协程：执行流，上下文信息以状态机形式保存在堆中
线程：执行流 + 栈（用来保存上下文信息）
进程：执行流 + 栈 + 地址空间资源（以及其他资源）

可以将上述三种概念总结为任务的概念：

任务 = 执行流 + 执行环境（包括地址空间资源、特权级、函数调用状态信息（栈））

调度器的调度代码可以认为是每个任务都共享（通过vDSO）的一段执行流，任务切换的边界是任务的执行环境发生变化的边界，或者执行流本身发生切换处（协程切换）。

在这个概念上，中断、异常、系统调用等都可以认为是任务间通信。

### 任务树

表达一个任务的管理层次。

任务树：“Hypervisor - 操作系统内核 - 任务”的树。

任务树的作用：
1. 发生中断、异常等情况时由谁处理
2. 任务的优先级逐层确定，上一层不需要看到全部的任务
3. 管理任务间通信

## 结构与功能

vDSO内部分为三个模块，任务调度模块、任务切换模块和trap处理模块。

- 任务调度模块：负责管理就绪队列、当前任务变量和任务的状态字段。
- 任务切换模块：负责进程、特权级和任务上下文的切换。
- trap处理模块：管理和调用trap处理函数，需要此模块的原因是任务切换模块接管了内核入口，因此需要在任务调度代码中集成trap处理功能。现在将trap处理包装成任务，参与调度过程。

vDSO外部的部分：暂无？

## 调度器与已有操作系统的功能范围

- 任务的定义：由操作系统提供。系统需要实现调度器要求任务具备的接口。
- 任务调度：就绪队列管理、当前任务管理、调度算法均由调度器提供。
- 任务切换：由调度器提供。
- trap处理：操作系统仍需提供trap处理任务。在trap进入内核时并需要处理trap时进入调度器，切换到trap处理任务。
- 任务的让出：系统负责提供用户使用的API，在其中设置任务状态为就绪，然后协程返回`Pending`。
- 任务的阻塞和唤醒：阻塞队列及阻塞操作由操作系统提供。调度器负责在调度循环中检测任务为就绪态还是阻塞态，从而决定是否将前一个任务放回就绪队列。任务的唤醒也由操作系统提供，且过程中会调用调度器的接口将任务放回就绪队列。

### 事件源

“事件源”是一个抽象类型，用于接收某一类型的事件或消息（例如IPC、系统调用）并将它们转化为对应的处理协程供调度器运行。事件源需要按优先级顺序提供不同的处理协程。事件源应具有以下接口：

- 获取当前该事件源中可运行协程的最高优先级（若当前没有协程可运行，则返回一个比最低优先级更低一级的优先级）
- 取出最高优先级的处理协程（取出的协程不需其它操作即可直接运行，例如一些需要给协程传递信息的事件源实现中，取出的协程应该已传递了对应的信息）（为了方便优先级位图的管理，该接口还要返回取出该协程后，新的最高优先级）

请求-响应队列结构是模块间通信（IPC、系统调用、软硬件通信）的常用方式。通过多态，可以将传统意义上的协程就绪队列、不同的请求-响应队列，以及外部中断控制器（例如riscv的PLIC）均实现为事件源：

- （带优先级的）协程就绪队列可以很简单地实现为事件源。从中取出的协程就是当前处于就绪状态的协程。
- 请求队列会使用一个协程处理队列中的所有请求。因此，从中的协程即为该处理协程，而最高优先级即为该处理协程的优先级。
- 响应队列的不同响应通常对应不同的协程，这些协程即为发出请求后阻塞等待响应的协程。为了将响应与对应的协程按照优先级排列并取出最高优先级的协程，可能需要采用多队列或者堆的结构。同时，在取出阻塞的协程前，需要通过一些方式将对应的响应传入协程内部。
- 外部中断控制器具备挂起中断并每次返回最高优先级的中断的功能，因此可以把中断优先级作为返回的最高优先级，把取出的中断对应的处理协程作为返回的协程。

### 调度器

文中其它部分所述的调度器为广义调度器，包括任务调度、任务切换、任务状态管理等功能。但本节中的调度器指狭义的调度器，仅包含决定下一个运行的协程这一项功能。

每个进程使用一个调度器，内核再使用一个调度器。也就是说，用户任务在每个地址空间中使用一个调度器，而内核任务共用一个调度器。而每个调度器都包含多个事件源。通过多态机制，一个调度器中的事件源可以为不同的类型。

用户态调度器包含的事件源：

- 本进程就绪队列
- IPC/异步系统调用队列
- 硬件队列（例如NVMe的队列）（仅限微内核架构）

内核态调度器包含的事件源：

- 内核就绪队列
- 异步系统调用队列
- 硬件队列（仅限宏内核架构）
- 中断控制器

在决定下一个运行的任务时，调度器首先从每个事件源获取最高优先级，计算出调度器最高优先级后，更新共享的本进程最高优先级字段（每个进程以及内核都需要维护自己的最高优先级并共享给所有地址空间）。再与其它地址空间的最高优先级比较，若自身的最高优先级不低于其它地址空间，则运行自身的任务；否则，切换到其它地址空间、运行该地址空间的调度器的任务。运行任务时，调度器从获取的优先级最高的事件源中拿出任务。如果多个事件源的最高优先级相同，则优先运行列表中靠前的事件源中的协程（因为它们的切换开销相对较低）。

在上文提到的多种事件源中，模块内部仅设置进程就绪队列和中断控制器作为事件源。再提供接口，使当前地址空间的调度器可以注册更多的事件源。

### 最高优先级的获取

为了降低调度器获取最高优先级的开销，可以在事件源内部设置活跃字段或预存最高优先级。

活跃字段：调度器获取最高优先级时，如果字段值为不活跃，则不在事件源内部查询最高优先级，而是直接返回最低的优先级。

- 对于有中断等额外通知方式的事件源（例如硬件队列），可以在事件源中不再有可运行协程时将它们设置为不活跃。当对应的中断到来，再将其重新设置为活跃。
- 对于将请求队列实现为事件源的情况，由于使用同一个协程处理所有的请求，因此可以在协程运行期间将事件源设置为不活跃，在协程因请求处理完而重新阻塞时将事件源重新设置为活跃。

预存最高优先级：通过一个变量存储最高优先级并在合适的时机更新，当调度器获取事件源的最高优先级时，直接读取该变量的值。。

以下情况可能导致优先级的提升。因此先更新对应事件源的最高优先级，再更新进程的最高优先级：

- 就绪队列：加入任务和取出任务时更新。
- 异步系统调用与IPC：可以由请求方写入请求队列时同时更新响应方的最高优先级；响应方写入响应队列时同时更新请求方的最高优先级
- 中断控制器：中断到来时本来就会打断当前执行流进入内核，使内核有机会更新自身的最高优先级
- 硬件：
  - 内核态处理硬件事件：
    - 硬件事件到来时有中断通知：在中断到来时得以在调度器中更新内核最高优先级
    - 硬件事件到来时无中断通知：在时钟中断时更新内核最高优先级
  - 用户态处理硬件事件：
    - 硬件事件到来时有中断通知：通过中断转发机制，让内核更新对应任务的最高优先级
    - 硬件事件到来时无中断通知：似乎无法及时更新进程最高优先级。而若进程没有协程可运行，其会被设置为最低优先级，导致难以被调度运行，也难以更新最高优先级。因此，可以在硬件驱动进程中创建一个稍低优先级的协程并循环执行yield，从而即使没有待处理事件时，进程的优先级也不会被设置为最低，因此后续还可被调度运行，并根据事件的到来更新最高优先级。

导致优先级下降的事件，即为从事件源中取出任务运行。取出任务的同时会返回事件源的新优先级。根据需要再次查询其它事件源的最高优先级，并计算出新的最高优先级。

### perCPU

由于一个调度器中的所有事件源不一定都是perCPU的，因此调度器的外层实现也不是perCPU的，也就要求事件源可以在多核环境下同步。为了降低同步开销，可以在事件源内部实现perCPU，例如在就绪队列中实现perCPU。

## 寄存器上下文保存的约定

原本的设计是让os传入寄存器上下文保存的接口，由调度器在合适时机调用。但在实现中遇到了问题：

- 对于线程上下文而言，上下文恢复后，执行流跳转到调用上下文保存函数的下一条代码。不过，由于接口限制，上下文保存和恢复必须是单独的函数，且设计的线程主动让权流程为“调用上下文保存函数->进入调度器”，因此除了上下文保存完毕后进入调度器以外，上下文恢复后还会进入一次调度器，不符合设计意图。
- 对于trap上下文而言，需要调用一个函数保存上下文意味着需要在函数外将调用者保存的寄存器保存在栈上；在函数内将被调用者保存的寄存器保存在栈上。而在保存上下文的函数中又要从栈上解析这些寄存器并存入上下文数据结构中，相当于进行了两次上下文保存，增加了开销。并且因为涉及编译器优化，保存了哪些被调用者保存的寄存器是不确定的，为寄存器的解析带来了困难。

因此，计划不再使用接口保存上下文，而是将这部分工作全部交给os进行，并约定这些保存上下文函数的执行流程。

需要对原有设计做如下修改：

- `Task` trait不再提供保存上下文的接口。（不过，恢复上下文仍使用接口进行）
- `trap_entry`和`thread_entry`不再包含保存上下文的部分。
- `ktrap_entry`和`utrap_entry`合并为一个函数。
- `trap_entry`中增加重新分配一个栈存储在`sscratch`/`uscratch`中的过程，因为trap处理过程中，`sscratch`/`uscratch`上原有的栈会被trap处理任务使用。

对上下文保存相关函数的约定如下：

- 线程上下文保存函数：
  - 类型：汇编语言实现的裸函数，没有分配/回收栈帧，没有自动保存被调用者保存的寄存器。
  - 参数：当前线程上下文指针
  - 流程：
    1. 将当前执行流的线程上下文保存在传入的指针指向的上下文结构中
    2. 跳转到调度器函数`thread_entry`
  - 调用时机：在线程需要主动让权时，先获取当前任务，获取其寄存器上下文指针，再调用该函数。
- 内核态trap上下文保存函数：
  - 类型：汇编语言实现的裸函数，没有分配/回收栈帧，没有自动保存被调用者保存的寄存器。直接作为trap向量。
  - 参数：无
  - 流程：
    1. 将栈切换到内核栈，并保存`sp`寄存器的先前值（可以通过`sscratch`实现）
    2. 在内核栈上保存第3~4步使用的寄存器
    3. 判断是否为特定系统调用号的系统调用（即为从用户态调度器陷入内核的情况），若是则设置`a0`为1，跳转到`ktrap_entry`。
    4. 从当前任务变量获取当前任务指针，加上一个硬编码的偏移量得到其寄存器上下文指针
    5. 将trap上下文保存在该上下文指针上。对于第2步已保存在栈上的寄存器，也需要加载并存储到上下文指针的对应位置中。
    6. 设置`a0`为0，跳转到`trap_entry`。
  - 调用时机：在触发内核态trap时，由硬件作为trap向量自动调用。
- 用户态trap上下文保存函数：
  - 类型：汇编语言实现的裸函数，没有分配/回收栈帧，没有自动保存被调用者保存的寄存器。直接作为trap向量。
  - 参数：无
  - 流程：
    1. 将栈切换到另一个用户栈，并保存`sp`寄存器的先前值（可以通过`uscratch`实现；该步骤需要已经预分配一个用户栈）
    2. 在用户栈上保存第3步使用的寄存器
    3. 从当前任务变量获取当前任务指针，加上一个硬编码的偏移量得到其寄存器上下文指针
    4. 将trap上下文保存在该上下文指针上。对于第2步已保存在栈上的寄存器，也需要加载并存储到上下文指针的对应位置中。
    5. 设置`a0`为0，跳转到`trap_entry`。
  - 调用时机：在触发用户态trap时，由硬件作为trap向量自动调用。

## 数据结构（TODO，需要后续逐步修改）

### 任务上下文

任务上下文结构位于TCB中，由操作系统提供。操作系统向模块中传入各种上下文切换（地址空间切换、特权级切换、线程切换）的接口（见上文），从而使模块可以进行上下文切换。

### 当前栈

当前栈变量以栈底指针形式存储，实现为perCPU的私有数据。在每个地址空间中，需要提供分配和回收栈的接口。

通过进入调度器的不同入口，可以得知调度器当前在空栈还是非空栈上运行。进而决定是否回收/切换栈。

由于栈随着线程上下文保存和恢复，当前栈变量也需要在这个时机保存和恢复。因此可能需要在线程上下文中增加栈底指针？

### 当前任务

每个CPU核心持有各自的当前任务变量，在同一个核心上跨地址空间共享。实现为vDSO共享数据中的数组，每个数组元素对应一个CPU核心。

当前任务以指针形式存储，且使用已初始化的虚函数表调用当前任务的方法。

当前任务相关的方法只会在任务所在的进程或者内核中调用。对当前任务的使用包括：保存当前任务的寄存器上下文；修改任务状态；将当前任务指针放回调度器（此过程中，需要获取当前任务是用户任务或内核任务）；更新当前任务指针。

### 当前调度器

当前调度器信息由四个变量组成：进程调度器指针（私有数据，非perCPU）、内核调度器指针（共享数据，非perCPU）、当前位于用户态或内核态的标志（共享数据，perCPU）当前地址空间（共享数据，perCPU）。（调度器实现为非perCPU的原因见[调度器/perCPU](#percpu)）

进程调度器指针只会在其所在的地址空间中调用（可能在用户态或内核态）。

对当前调度器的使用包括：更新当前进程最高优先级（需访问进程调度器）；更新当前调度器变量；从调度器中取出最高优先级的任务。

### 最高优先级

每个调度器维护自身的最高优先级并共享。实现为共享数据中的数组，数组包含三项：第一项为0代表内核调度器；非0代表进程调度器，且取值代表进程所在的地址空间。第二三项分别代表最高优先级和调度器指针。

### 调度器数据结构

使用`Vec`存储一系列事件源，优先级相同时优先选择靠前的事件源（见[调度器章节](#调度器)）。

`Vec`的元素包含：

- 事件源结构指针
- 事件源虚函数表指针
- 活跃标志（见[调度器章节](#调度器)）
