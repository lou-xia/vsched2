## 总体路线图

总顺序可以压成一句：

> **规则 → 入口 → Q 台账 → 模块卡 → 深契约 → 设计 → 状态/计划 → 归档。**

每一阶段是下一阶段的输入。不要跳过“模块卡”直接重写设计，否则设计仍会建立在不准确的现状上。

| 阶段 | 核心产出 | 完成标准 | 粗略工作量 |
|---|---|---|---|
| 1. 入口与规则 | `README.md`、`AGENTS.md`、`doc/README.md`、`GLOSSARY.md`、`doc/questions.md` 第一遍 | 新会话能导航；旧 TODO 都有 Q-ID | S |
| 2. 全仓契约卡 | `reference/README.md`（覆盖矩阵）、`reference/module-map.md`（约 9 张卡） | 每个模块一张卡，卡里无算法 | M |
| 3. 深契约 | `interfaces`、`shared-data`、`state-machine`、`concurrency`、`build-and-test` | 前置/后置、所有权、不变量可指到代码 | L |
| 4. 设计文档 | `design/README.md` + 6 篇 design + `analysis/reentrancy/` | 每篇有目标/非目标/不变量/Q；路径表可读 | L |
| 5. 状态与计划 | `status.md`、`plans/README.md`、首个 design-readiness 计划 | 每个 gap 有链接；每个 step 过就绪检查 | S |
| 6. 归档与维护 | `archive/README.md`、教训提炼、维护规则 | archive 只读；已解决结论有活文档对应 | S |

## Phase 1：入口与规则（半天到一天）

产出：

- `README.md`：项目一句话、当前阶段、三个入口。
- `AGENTS.md`：AI 路由 + 硬规则（无裸 TODO、接口改动必须给理由、archive 只读）。
- `doc/README.md`：文档地图、生命周期、阅读路径、代码→文档归属。
- `doc/conventions.md`：类型、状态机、front matter、ID、命名与链接规则。
- `doc/maintenance.md`：按场景的维护规则。
- `GLOSSARY.md`：先收 10–15 个有歧义的术语，带代码符号列。
- `doc/questions.md`：第一遍只扫描现有文档里的 `TODO/暂无/待定/需要进一步考虑`，每个变一条 Q，不求解。

在 `doc/conventions.md` 里先定死：状态词表、ID 前缀（`Q-/D-/I-/PATH-`）、front matter 字段（`status/depth/verified_at/applies_to`）、文件命名、归档策略。

**验证**：新会话只读入口三件套，能回答“项目是什么、现在到哪、改 X 看哪、术语 Y 对应哪个符号”。

## Phase 2：全仓契约卡（一到两天）

产出 `reference/README.md` + `reference/module-map.md`，按领域分约 9 张卡：

`schedule`、`block_and_wake`、`stack`、`arch`、`current`、`interface`、`api`、`main_loop`、`build/vDSO 集成`。

每张卡 10–20 行：职责、公开接口、依赖、所有权、不变量、易错点、`depth: card`、`verified_at`。**不写算法流程。**

**验证**：每个 `src` 模块在覆盖矩阵中恰有一行；每行有卡；卡里的符号能在代码中找到；空单元格有原因。

这一步会冒出一批新 Q，随手进 `questions.md`。

## Phase 3：深契约（两到四天）

严格按这个顺序：

1. `interfaces.md`：7 个 trait + C ABI，谁实现/谁调用/前置/后置/目标改名。
2. `shared-data.md`：VVAR、私有数据、per-CPU、用户/内核两份拷贝，写者/读者/同步。
3. `state-machine.md`：`TaskState` × `SchedAction` × 上下文类型，谁在何时改。
4. `concurrency.md`：锁清单与锁序、关中断边界、per-CPU 写者、栈所有权、`I-xx` 不变量。
5. `build-and-test.md`：目标、feature、`CPU_NUM`、`vdso_builder`、验证方式。

只写重构需要的那部分，不写全量实现说明。

**验证**：每条前置/后置/不变量能指到代码；没有逐行翻译；design 能直接引用这些锚点。

## Phase 4：设计文档（三到五天）

顺序：

1. `design/README.md`：索引、依赖图、状态。
2. `task-model.md`：任务/线程/协程/任务树/上下文类型。
3. `os-boundary.md`：OS 与调度器各自负责什么。
4. `scheduler.md`：事件源、优先级、per-CPU、共享。
5. `scheduling-loop.md`：入口出口、路径枚举、trap、栈。
6. `blocking.md`：阻塞队列、Waker、丢失唤醒。
7. `reentrancy.md` + `analysis/reentrancy/`：目标设计、判定标准、时间×空间矩阵。

来源是拆分现有的 [共享调度器模块设计文档](<draft/新版设计/共享调度器模块设计文档.md>)、[共享调度器模块代码实现设计](<draft/新版设计/共享调度器模块代码实现设计.md>)、[数据结构修改](<draft/新版设计/数据结构修改.md>)、[调度器可重入设计文档](<draft/可重入分析/调度器可重入设计文档.md>)。是拆和重写，不是原样搬。

每篇固定栏目：本文回答/不回答、问题/目标/非目标、模型、规则与不变量、路径/时序、接口影响、未决 Q、验证。

注意两点：

- 路径表按维度重排，加“实现状态”列；不要在一张表里塞六个维度。
- `P1..Pn` 判定标准先补全，再填矩阵；`P3/P4` 现在是空的，这是设计文档的前置条件。

**验证**：每篇没有裸 TODO；每个“已实现/目标/待定”都有标记；每条设计断言能指到 reference 或 Q。

## Phase 5：状态与计划（半天到一天）

- `doc/status.md`：能力 × 目标设计 / 代码实现 / 验证 / 差距 / 相关 Q。
- `doc/plans/README.md`：计划状态（`draft/not ready`）、阻塞 Q、路线图（方向，不是承诺）、已就绪步骤表。
- 如果实现计划还不成熟，先建 `plans/0001-design-readiness/`：Step 1 补 P1..Pn、Step 2 定上下文栈、Step 3 定状态机/`Blocking`、Step 4 定事件源命名。
- 每个 step 过“就绪检查”：改成什么已定、接口影响已知、完成标准可验证。任一为否，它是 Q 或 spike，不是 step。

**验证**：status 每个 gap 有链接；plan 里没有占位步骤。

## Phase 6：归档与维护（半天到一天）

- `doc/archive/README.md`：每轮迭代的目标、结论、仍有效的结论、被谁取代。
- 归档前提炼：
  - [调度器的问题](<archive/1.初版实现/调度器的问题.md>) 的栈接口、sp/base → `reference/module-map.md` 的 stack 卡或 `reference/concurrency.md`；
  - [当前问题](<archive/2.清晰调度器边界修改/当前问题.md>) 的状态锁死锁 → `concurrency.md` 的 `I-xx`；
  - [清晰调度器边界修改计划](<archive/2.清晰调度器边界修改/清晰调度器边界修改计划.md>) 的 action/阻塞唤醒 → `design/blocking` + decisions；
  - trap 事件源 → `design/scheduling-loop` 或 decisions。
- 链接与图片审计：当前无缺失；新增缺失记录到 `doc/archive/README.md`。
- 维护规则写进 `AGENTS.md`：改代码同 commit 更新 reference；`verified_at`；无裸 TODO；Q 关闭时落到 ADR/design；step 完成后归档并更新 status。

**验证**：archive 里每条“已解决”都能在活文档中找到对应；没有活文档把 archive 当现状引用。
