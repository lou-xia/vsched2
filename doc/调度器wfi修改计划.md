# 调度器wfi修改计划

## 问题1

问题：`wait_for_runnable_task`函数中入队和睡眠的同步问题。现有设计在休眠前检查了两次调度器，确认没有任务取出时才会休眠；但仍是“先检查再休眠”的顺序，有可能出现以下情况：待休眠核心检查调度器 -> 活跃核心将任务放入调度器 -> 活跃核心判断待休眠核心未休眠，不需唤醒 -> 待休眠核心休眠，导致上述核心在休眠后无法被唤醒。

解决方案：

在`current.rs`中新增per-cpu的共享数据`IS_SLEEPING`，指示每个核心是否将要或正在休眠。在`wait_for_runnable_task`函数中，在第二次检查调度器之前设置`IS_SLEEPING`。第二次检查若发现有任务，则在返回前清除`IS_SLEEPING`。其它逻辑与原有相同。

对于唤醒核心的内容，则如下设计。因为目前还未实现唤醒核心的逻辑，因此这一段的内容不需要在这一步内进行。活跃核心根据`IS_SLEEPING`判断有哪些核心在睡眠，并向`IS_SLEEPING`的核心发送中断唤醒。

## 问题2

问题：目前对中断的上下文是否在调度器中（`trap_entry`中的`scheduler_waiting`变量）是通过比较当前任务是否为`SCHEDULER_WAIT_CONTEXT`，也就是`init_task`来判断的。但这会导致`init_task`本身被中断时，调度器会误判为中断上下文在调度器中，导致逻辑错误。其也会导致`init_task`的上下文被覆盖，若后续`init_task`自身再次执行，就会进入错误的上下文。

解决方案：

对于`scheduler_waiting`的判断标准的问题，可以在`trap_entry`中检查当前的`IS_SLEEPING`，若为true则说明中断上下文在调度器中。且检查后应将`IS_SLEEPING`设为false。

对于`init_task`的上下文被覆盖的问题，在初始化函数中不再使用`init_task`初始化`SCHEDULER_WAIT_CONTEXT`，而是通过`TrapInfo::new_handler`接口创建的新的任务初始化`SCHEDULER_WAIT_CONTEXT`。由于这里创建的任务仅作为上下文的容器，并不会执行初始化时传入的任务的内容，因此`new_handler`的参数传入空指针，以方便该任务在意料之外运行时，快速定位问题。

## 问题3

问题：目前仅在没有任务时实现了核心的休眠，未在获得任务时实现核心的唤醒。

解决方案：在`ReadyQueue`的`push_task`方法中，更新就绪队列优先级后，若就绪队列的任务数大于某个阈值，则检查其它核心的`IS_SLEEPING`变量，若有正在睡眠的核心，则选择一个核心，向其发送核间中断以唤醒。
